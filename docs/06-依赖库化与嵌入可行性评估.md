# 依赖库化与嵌入可行性评估

> 目标：将 [docs/00-长期个人智能体记忆系统方案.md](./00-长期个人智能体记忆系统方案.md) 设计的记忆系统做成**可被其他系统调用的依赖库**，并支持**嵌入其他系统**（进程内/侧车/MCP 三种形态）。
> 状态：可行性评估（v1.0，2026-08-03），评估通过后按 [07-系统架构设计.md](./07-系统架构设计.md) 实施。

---

## 1. 评估目标与约束

| 项 | 要求 |
|---|-----|
| 调用方式 | 作为依赖库（pip install）被其他系统 import 调用 |
| 嵌入方式 | 进程内嵌入（首选）、可选侧车 HTTP、可选 MCP 服务 |
| 存储 | 单用户本地优先，不强制外部数据库服务 |
| 语言生态 | 核心 Python 3.10+（当前环境 3.12.4） |
| 数据模型 | 按方案 00：nodes / edges / facts / versions / tombstones |
| 检索 | 三路召回（时间/图谱/语义）+ RRF，MAP/Recall 评测门禁 |
| 外部依赖 | LLM 能力（抽取/判题/嵌入）可注入回调，不绑定厂商 |

## 2. 现状盘点（可行性的事实基础）

### 2.1 模拟代码已具备可复用内核

`simulation/dna_helix_memory_sim.py` 中的 `MemorySystem` 已实现方案 00 的全部核心机制，且公共方法形态已接近库 API：

`add_event / add_entity / add_edge / add_fact / recall(query, k, mode) / neighbors / fact_lookup / access / step_day / resolve_conflicts / tombstone / version`

结论：**核心逻辑不是从零写，而是从模拟代码中抽取、适配与加固**，可行性高。

### 2.2 运行环境已验证

| 依赖 | 状态 |
|-----|-----|
| Python 3.12.4 | ✅ 可用 |
| sqlite3 3.45.3（标准库） | ✅ 可用，无需安装 |
| numpy 1.26.4 | ✅ 可用（向量兜底检索） |
| sqlite-vec（Windows x86_64） | ✅ 官方支持 loadable extension（vec0.dll） |
| FastMCP / MCP Python SDK | ✅ 生态成熟（FastMCP 1.0 已并入官方 SDK） |

### 2.3 关键工程事实

- SQLite 是进程内数据库，天然适合"嵌入其他系统"；WAL 模式下单写多读，配合 `busy_timeout` 与库内写锁可满足单进程并发。
- 向量检索两条路都可行：`sqlite-vec`（扩展加载，需随包分发 vec0.dll）或 `numpy` 暴力检索（零额外依赖，万级节点可接受）。
- 侧车形态用 FastAPI + uvicorn 即可；MCP 形态用 FastMCP 暴露 `write_memory / recall / forget` 工具。

## 3. 四种集成形态的可行性

| 形态 | 说明 | 可行性 | 适用场景 |
|-----|-----|-------|---------|
| A. 进程内库（主推） | `pip install dnamemory`，`from dnamemory import MemorySystem` | ✅ 高：纯 Python + SQLite，无服务依赖 | Python Agent/服务直接嵌入 |
| B. 侧车 HTTP | `dnamemory[server]`，FastAPI 本地端口 | ✅ 高：FastAPI 生态成熟 | 非 Python 系统、多进程隔离 |
| C. MCP 服务 | `dnamemory[mcp]`，FastMCP 暴露工具 | ✅ 高：MCP 已成为 Agent 集成标准 | Claude/Codex/任意 MCP 客户端 |
| D. 远端共享后端 | `dnamemory[pg]`，PostgreSQL + pgvector | ✅ 中：需外部服务，放后续阶段 | 多设备同步、多人/多 Agent 共享 |

推荐路径：**A 为主交付，B/C 作为可选 extra 与 A 共用同一内核**；D 作为二期能力。

## 4. 逐项可行性判断

| 维度 | 判断 | 依据 / 风险 |
|-----|-----|------------|
| 打包分发 | 可行 | pyproject.toml + wheel；核心零强制依赖，可选 extras |
| 存储嵌入 | 可行 | SQLite 文件或 `:memory:`；DDL 已在方案 00 |
| 并发 | 可行 | WAL + busy_timeout + 库内写锁；读并发不受限 |
| 向量检索 | 可行 | sqlite-vec（Windows 已支持）或 numpy 兜底；无网环境可降级双路 |
| 跨平台 | 可行 | Windows/macOS/Linux；sqlite-vec 均提供预编译扩展 |
| LLM 解耦 | 可行 | Extractor/Embedder/Judge 回调协议，默认确定性实现，不锁厂商 |
| 评测门禁 | 可行 | 模拟实验 8 的指标代码可抽取为 `metrics` 模块 |
| 迁移成本 | 低-中 | 从单文件模拟拆包，预计 1-2 天；需补齐类型校验与线程安全 |
| 安全边界 | 可控 | 库不执行任意代码；MCP/HTTP 形态需鉴权（token）与路径白名单 |

## 5. 结论：可行性高，建议进入架构设计

**判定：可行（High）**。核心理由：

1. 核心机制已实现并有评测门禁（MAP@5=0.928、双路召回 1.000），不是从零发明；
2. 存储与向量方案在目标平台（Windows + Python 3.12）已验证；
3. 三种嵌入形态共用同一内核，工程量递增但不推倒重来；
4. LLM 回调协议保证库本身无厂商绑定，任何系统都能嵌入。

主要风险与对策：

| 风险 | 对策 |
|-----|-----|
| 模拟代码为单文件，拆包引入回归 | 抽取后立即跑实验 1-8 全套指标做回归 |
| sqlite-vec 在某些平台缺失 | 自动探测，失败回退 numpy / 双路检索 |
| API 被外部系统依赖后难以演进 | 冻结核心 API 为 v1；新能力走可选参数/新方法 |
| MCP/HTTP 暴露敏感记忆 | 默认 local-only 绑定、token 鉴权、路径白名单 |
