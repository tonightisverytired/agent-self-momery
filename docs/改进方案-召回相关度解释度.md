# 改进方案：召回 · 相关度 · 解释度（0.8.1 改进迭代）

> 依据：2026-09-18 实测评估（门禁/状态评测/长期能力/LCCC 真实语料探针 + 代码走查）。
> 本文含问题诊断、改进方案（IA-1~IA-5）与开发计划（阶段 A~E）。

## 1. 问题诊断（实测数据）

| 现象 | 数据 | 根因（代码定位） |
|---|---|---|
| 真实语料召回崩塌 | 同一套长期能力查询：21 事件玩具库 1.0 → 810 事件 LCCC 库 **0.15** | `retrieval.py:101-114` `_semantic_path`：正则 `[0-9a-zA-Z\u4e00-\u9fff]+` 把整句中文切成**一个** token，再做整串子串匹配——自然问句几乎永不命中 |
| bge-m3 反而拉低精确名召回 | 全名自召回：无向量 1.0 → bge-m3 **0.5** | `retrieval.py:260-268`：注入 embedder 后词面路被稠密路**整体替换**，cosine≥0.55 阈值把短实体名精确匹配稀释掉 |

## 2. 改进方案

### IA-1 写入端证据链自动闭环（解释度根基）

- `write_text`/`write_many` 把原文透传至 `_write_candidates`（`meta["_raw_text"]` 内部键）；
- 批内无 evidence 候选时**自动合成批级证据**：`source_type=meta.get("source_type","conversation")`、`source_ref`=原文截断、`content_hash=sha1(原文)`、`conversation_id/message_id/observed_at` 取自 meta，绑定批内全部候选；幂等键 `auto:{sha1}` 防重放重复；
- 公共 API 对齐：`add_fact`/`add_event`/`add_entity` 增加 `evidence_ids` 参数（store 层已支持，仅门面未暴露）；
- server `/write`、`/batch` 请求体补可选 `meta` 透传字段。

### IA-2 中文召回修复（召回根基）

- `_semantic_path` 重写为**字符 bigram 包含度**打分（中文免分词；复用 `memory.py:874-886` 同款思路）：`score = max(containment(q, name), containment(q, description)) × value_score`，含 `q ⊂ hay` 短路 1.0、单字回退子串；新增配置 `lexical_min_score`（默认 0.2）过滤噪声；
- embedder 注入时**词面路与稠密路并行**（独立 RRF 贡献路径 `lexical`/`semantic`），稠密阈值不变——语义增益保留，精确名命中不再被稀释；
- `MemoryHit` 增加 `path_scores`（每路原始分+rank），API `/recall` 响应透出。

### IA-3 上下文相关度收口（验证+补强）

- 验证 `_query_scope` 收口后 causes/impacts/patterns 不再全库灌水（重测 probe trace）；
- current_state 维持"状态层全库裁决"原则（docs §30），靠 IA-2 提升 `_relevance` 命中率使相关事实自然置顶；门禁断言答案可得率。

### IA-4 解释性暴露

- `serializers.py`：evidence 全字段（content_hash/trust_level/conversation_id/message_id/observed_at/metadata）；conflict 保留 facts 列表；current_state 各项附 `memory_score` 六分项；
- `explain()`：kind=fact 整合 `fact_history` 版本链；related 边带 confidence；
- 裁决审计落库：`supersede_fact`、冲突裁决、FactResolver 裁决链写 `audit_log`（含裁决依据字符串）；新增 `GET /audit` 查询端点；
- `coherence` explanations 进 `ctx.notes`。

### IA-5 评测门禁升级

- `gate_check.py` 增加**合成干扰集探针**：快照库注入模板化干扰事件 + 自然问句查询（非实体名同构），锁住 bigram 词面路的 paraphrase 召回下限——不依赖外部数据的回归门；
- `relevance_probe.py` 加 `--gate` 阈值退出码，纳入发布前检查；
- 修复后更新 README 验证状态表与功能清单（实测数字）。

## 5. 实施结果（2026-09-19 实测回填）

阶段 A~E 全部完成。实施中额外发现并修复三个方案外问题：

1. **DeepSeek 托管模型行为漂移**——同名 `deepseek-v4-pro` 产出候选量较 9-15 基线腰斩（fact 167→26、belief/intent 归零）；对拍后注入脚本改用 `deepseek-chat`（可用 `DEEPSEEK_MODEL` 覆盖），并在 SYSTEM_PROMPT 增加状态维度抽取要求。重注入后 LCCC 库：fact 191 / belief 206 / intent 127 / evidence 72（批级 100% 覆盖）。
2. **词面路价值分稀释**——`containment × value_score` 让高价值分弱相关节点挤掉精确匹配；得分改为 `containment × (0.5 + 0.5 × value_score)`，与稠密路「语义为主、价值为辅」同构。
3. **短名实体灌榜 / 实体锚消失的双向困境**——对称子串短路（`hay in q → 1.0`）让「用户」类高频实体满分灌满榜首；取消短路又让「公公的健康状况是什么」的主语实体掉出候选池（答案率 0.367→0.167）。最终方案：短路仅 `q ⊂ hay → 1.0`，另加实体锚定保底（节点名 ≥2 字且为查询子串 → 0.5），进得了候选池、压不过全覆盖事件。
4. **上下文「最后一公里」**（答案可得率 0.233→0.367 后仍卡住）——根因有三：`_relevance` 用 RRF 融合分（~0.01）做实体锚定，被 key 族/value 项淹没；current_state 预算内 191 条事实按「常数基线 3.4 + 微弱相关分」排序，相关事实浮不出；key 族映射只有「位置」一族。修复：锚定改用词面路原始分、ContextBuilder 两阶段收口（相关事实先进预算，状态裁决仍全库）、`_relevance` 增加 key 直配（查询含 key 原文 → 1.0，bigram 重叠弱信号）。答案可得率 → **0.833**。

## 6. 三轮改造：个人助手场景（2026-09-20）

### 6.1 场景判定与依据

目标场景明确为**个人 AI 助手 / 单用户 agent 记忆层**。两项实测定位瓶颈：

**性能剖析**（cProfile，规模库 3 次 recall_context，模型嵌入仅占 1.8s/50s）：

| 热点 | 规模 | 根因 |
|---|---|---|
| fetch_nodes / fetch_edges | 每次查询重复 7 次 / 10 次全表解析 | 无缓存，且文件库每读一次新建连接 |
| `_dt` 时间解析 | 211 万次调用 | 同一时间串跨行反复 parse |
| json.loads | 26 万次 | 随 fetch 重复解析 evidence_ids |
| `_memory_score` 内层 genexpr | 1358 万次 | current/history 身份判定 O（事实²） |

实测延迟（CPU，9374 节点）：recall top-10+reranker p50 0.93s；recall_context p50 **4.3s / p95 7.5s**。

**answer 口径失败归因**（D 组全部失败样本）：profile/social 失败（奖项/雇主/教育背景/关系标签）**事实都在库里**，是上下文预算挤压——根因：`key_query_words`/`key_aliases` 只有「位置」一族，且 PerLTQA 画像 key 为英文（Employer/Achievements/…），中文查询永不命中 key 族；dialogues 失败为指代式提问（语义鸿沟，留待四轮）。

### 6.2 改造项（本轮执行，评测闭环除外）

| 序 | 项 | 内容 | 文件 |
|---|---|---|---|
| T1 | 读快照缓存 | fetch_* 按 `_data_version` 缓存解析结果，版本内共享；唯一突变点（证据校验降置信）改 copy-on-write | store.py, memory.py |
| T2 | 时间解析缓存 | `_dt` 对 str 输入走 lru_cache（datetime 不可变，共享安全） | store.py |
| T3 | 打分索引化 | `_memory_score` 的 current/history 身份判定改预算 id 集，O(N²)→O(N) | memory.py |
| T4 | 启动预热 | `create_app(warmup=True)` 默认开，lifespan 内小 recall 预热模型与读缓存 | server/api/app.py |
| T5 | key 族扩充 + 分层相关性 | key_aliases/key_query_words 从 1 族扩到 13 族（含英文 key 与 `关系_*` 前缀规则）；`_relevance` 族命中分层：主体锚定+族命中=1.0，仅族命中=0.3（防多主体库灌榜） | models.py, resolve.py, memory.py |

**本轮不做**（用户指示）：生成式评测（DeepSeek 裁判）、对话摘要节点——后者待评测口径闭环后验证再扩。PG 后端暂不加快照缓存（行为正确仅不加速）。

| 指标 | 改前 | 改后 |
|---|---|---|

| `_relevance` 族词扫描 | 逐事实重扫 13 族 | `_query_families` 按查询预算 |

剩余延迟主要是嵌入推理（~0.2s/查询）与 reranker 交叉编码（CPU 模型绑定成本），非标量管道。

**answer 口径点验**（D 组 6 条原失败样本，不经评测套件）：**5/6 修复**（奖项×2/雇主/教育背景/邻居均进上下文）；唯一未过「王小明和赵明的关系」期望「熟人」而库中事实为「朋友」——近义词锚点差异，hit 类口径结构性不可赢，需生成式评测判定。

**关键设计修正**（实施中发现）：key 族别名不能直接并入 `key_aliases`——它同时驱动**裁决分组**（同节点同 canonical 只留一条 current），把 Title/Occupation、Achievements/Awards 这类**不同属性**合并会互踢出 current_state。最终拆分为：`key_aliases`（裁决级，只并真同义）+ `key_query_aliases`（查询级宽族，含「族_实例」前缀规则，仅 `_relevance` 用）。族命中分层：主体锚定+族命中=1.0，仅族命中=0.3（防多主体库灌榜）；另加**实体锚定进候选**：查询提及的节点名（person ≥2 字，其它 ≥3 字，最多 5 个）保证进 recall_context 候选，锚分 0.5。

**服务端**：`create_app(warmup=True)` 默认开，lifespan 内小 recall 预热模型与读缓存。

**遗留**：① recall_context 剩余 ~1.4s 中嵌入+reranker 占大头，可再调 rerank_top_n 或 recall_context 的 k=40；② 对话摘要节点与生成式评测留待下轮（评测口径闭环后验证）；③ PG 后端未加快照缓存（行为正确，仅不加速）；④ `key_query_words` 可按真实查询日志继续扩词。

## 7. 四轮改造：生成式评测闭环 + 对话摘要节点（2026-09-21）

### 7.1 生成式评测口径（ops/eval_perltqa_gen.py）

hit/锚点口径是代理指标，且对细粒度层、近义表述（「朋友」vs「熟人」）结构性
不利。新口径走真实链路：`recall_context` 上下文 → DeepSeek 生成回答 →
DeepSeek 裁判对照标准答案判语义对错（temperature 0，两题一评，失败进
错误桶）。抽样逻辑与 eval_perltqa.py 完全一致（同 seed/同 ctx-per-cat），
并同条记录锚点命中供口径对拍。

**基线（0.8.2 + reranker，n=629 分层抽样，0 错误）**：

| 口径 | overall | profile | social | events | dialogues |
|---|---|---|---|---|---|
| **生成式答对率** | **0.8188** | 0.955 | **0.644** | 0.854 | 0.828 |
| 同样本锚点包含 | 0.9222 | — | — | — | — |

锚点口径系统性高估约 10 个点；social 在生成式口径下才是真短板（0.64）。

**基线暴露的新失败模式**：① 过度枚举——上下文同时含正确答案与干扰项，
生成器罗列候选（「老邻居是谁」gold「赵晓」gen「赵晓、李磊」），锚点命中
但判错——已修生成提示词（唯一答案只答最确定的一个）；② 配角人物属性
稀疏（数据侧）；③ 指代/聚合型对话提问——摘要节点对症。

**主体偏好修复**（随评测落地，库代码）：查询点名的实体（person ≥2 字、
其它 ≥3 字，≤5 个）不仅锚定进候选，其事实在 `current_state` 预算分配中
优先（`ContextBuilder.build(prefer_nids=...)`）——多主体库下同族事实
灌榜会把被问主体的答案挤出预算（生成式冒烟曾因此 4 题仅对 1）。

### 7.2 对话摘要节点（ops/ingest_perltqa_summaries.py）

为 >200 字的 chat 会话生成 DeepSeek 摘要节点（kind=chat_summary，
value_score 0.6，≤120 字，保留人名/结论/计划），边结构
`persona --discusses--> 摘要 --summarizes--> 会话`。幂等键
`perltqa:sum:{session_id}` 支持断点续跑。

### 7.3 复测结果（回填）

**摘要注入**：1741 条摘要 + 3482 条边，0 错误（`ops/data/perltqa_summary_report.json`）。

**生成式复测**：跑到 60% 时 DeepSeek 账户余额耗尽（402 Payment
Required），255 条进错误桶，有效样本 374 且类别构成偏移，**与基线不可比，
摘要节点收益未验证**（部分结果 0.7968 仅供参考）。基线 0.8188（n=629）
是当前可靠锚点。

**状态与回滚口**：摘要节点保留在库中（幂等键 `perltqa:sum:*`）；若下次
评测显示稀释召回，按 `kind='chat_summary'` 整类删除即可。生成式评测脚本
支持断点重跑（错误桶重跑即可补齐）。
