# dnamemory 业务与项目演进

> 当前基线：0.3.0 MVP  
> 下一阶段：0.4.0 Memory State / Temporal Memory  
> 后续方向：0.5.x Associative & Impact Memory → 1.0 Memory Runtime  
> 项目定位：长期个人智能体记忆系统 / 可嵌入式 Memory Runtime

---

## 1. 演进总览

### 1.1 项目最初解决的问题

dnamemory 最初的目标是解决 Agent 的跨会话长期记忆问题：把事件、实体、事实与关系持久化，并通过时间、图谱、稠密、稀疏多路召回，让 Agent 在后续会话中能够找到历史信息。

0.3.0 已经完成了一个完整 MVP 的基础闭环：

```text
写入
  ↓
结构化 Memory
  ↓
SQLite 持久化
  ↓
Time / Graph / Dense / Sparse Recall
  ↓
RRF
  ↓
Top-K Memory
```

同时具备：

- 事件 / 实体 / 关联边 / 事实模型；
- 双时态 `valid_at / invalid_at`；
- `superseded_by` 事实版本链；
- 冲突治理；
- 生命周期与受控遗忘；
- 实体消解；
- 反射压缩；
- sqlite-vec；
- FastAPI / FastMCP / CLI；
- 中文五类长期记忆评测集。

现有需求文档明确将系统定位为可嵌入、可调用、零配置的长期智能体记忆库，并以多路召回、治理、生命周期和评测为基础能力。fileciteturn0file1L5-L15

---

## 2. 为什么必须进入下一阶段

0.3.0 的主要问题不是“召回不够”，而是**召回结果仍然是 Candidate Memory，而不是可直接作为长期认知状态使用的 Memory State**。

当前架构已经能够回答：

> “什么记忆和当前 Query 比较相关？”

但长期智能体真正需要继续回答的是：

> “这些记忆现在分别是什么状态？”
>
> “哪些是客观发生，哪些是用户观点？”
>
> “事实后来有没有变化？”
>
> “观点为什么发生变化？”
>
> “一件事带来了哪些正向和负向影响？”
>
> “这些结果的先后顺序是什么？”
>
> “这个判断的证据在哪里？”
>
> “不同记忆维度之间是否自洽？”

因此项目开始从：

```text
Memory Retrieval System
```

演进为：

```text
Memory Runtime
```

# 4. 阶段二：判断“现在是什么状态”——0.4.0

这一阶段是当前项目最重要的一次业务升级。

## 4.1 从 Memory Record 升级为 Memory State

新增：

```text
Fact
Event
Belief
Intent
Evidence
```

形成：

```text
Entity
 ├── Event
 ├── Fact
 ├── Belief
 ├── Intent
 └── Evidence
```

其中：

- Event：发生了什么；
- Fact：当前 / 历史状态是什么；
- Belief：主体怎么看；
- Intent：主体准备做什么；
- Evidence：为什么相信；
- Entity：记忆属于谁 / 什么对象。

---

## 4.2 从“相似记忆”升级为“当前有效记忆”

例如：

```text
2025-01
city = 南京

2026-01
city = 上海
```

查询：

> 用户现在在哪里？

系统不能简单返回两个 Top-K，而应该由 `FactResolver` 根据查询时刻解析：

```text
当前状态：上海
历史状态：南京
变化时间：2026-01
证据：xxx
```

即：

```text
Recall
  ↓
Candidate Facts
  ↓
Version Resolution
  ↓
Current State
```

# 5. 阶段三：理解“我怎么看”——Belief Memory

这是从普通长期记忆向“长期认知记忆”演进的关键阶段。

## 5.1 Fact 与 Belief 分离

例如：

```text
Fact:
用户目前住上海

Belief:
用户认为上海生活成本高

Intent:
用户考虑离开上海
```

三者同时成立，不构成冲突。

---

## 5.2 观点不覆盖，而是演化

历史：

```text
2025-01
上海工作机会很多

2026-01
上海生活成本太高

2026-08
上海工作机会依旧不错，但不适合长期生活
```

系统保存的不是一个最终摘要，而是：

```text
B1 → B2 → B3
```

回答当前观点时：

```text
当前 Belief
+
历史 Belief
+
Belief Change
```

共同形成用户长期认知状态。

---

# 6. 阶段四：理解“事情带来了什么结果”——Impact Memory

这是在现有业务演进基础上新增的重要能力。

## 6.1 为什么必须增加 Impact

单独记录：

```text
Event:
用户换工作
```

无法解释：

> 换工作到底给用户带来了什么？

因此新增：

```text
Impact
```

定义：

> 某个事件、行为或决策对主体产生的结果、变化或影响。

---

## 6.2 Impact 的三层表达

### Direction

表示发生了什么变化：

```text
increase
 decrease
stable
appear
disappear
```

### Valence

表示评价方向：

```text
positive
negative
neutral
mixed
unknown
```

### Magnitude

表示影响程度：

```text
0.0 ~ 1.0
```

例如：

```text
Event:
换到上海工作

Impact 1:
收入 increase
valence = positive
magnitude = 0.7

Impact 2:
工作压力 increase
valence = negative
magnitude = 0.8
```

注意：

> Direction 和 Valence 不能混为一谈。

“增加”本身不代表好或坏。

---

# 7. 阶段五：从“好 / 坏”升级为“多维影响”

长期记忆不能简单采用：

```text
这件事 = 好事
```

更合理的是：

```text
事件
 ├── 收入      +
 ├── 工作时间  -
 ├── 成长      +
 ├── 压力      -
 └── 满意度    +
```

形成多维 Impact Profile。

---

## 7.1 Impact Dimension

推荐支持以下通用维度：

```text
income
work
health
stress
relationship
time
learning
satisfaction
risk
cost
quality
convenience
```

但不强制固定枚举，应允许业务扩展。

---

## 7.2 评价主体必须显式保存

例如：

> 公司给我涨工资了，但我压力反而更大。

不能简单保存：

```text
涨工资 = positive
```

而应拆成：

```text
Objective Impact:
income ↑

Subjective Impact:
pressure ↑
valence = negative

Evaluator:
user
```

因此 Impact 需要区分：

```text
objective
subjective
```

并记录：

```text
evaluator
```

---

# 8. 阶段六：时间链与影响链

## 8.1 Temporal Chain

回答：

> “事情是怎么一步步发生的？”

例如：

```text
2025-01
进入上海工作
   ↓
2025-03
收入提高
   ↓
2025-05
开始加班
   ↓
2025-08
压力增加
   ↓
2026-01
开始考虑离职
```

---

## 8.2 Impact Chain

回答：

> “事情产生了什么结果？”

例如：

```text
换工作
 ├──→ 收入提高
 │      └──→ 消费能力提高
 │
 └──→ 工作时间增加
        └──→ 睡眠下降
              └──→ 压力提高
```

Temporal Chain 解决“什么时候”。

Impact Chain 解决“造成了什么”。

两者可以交叉：

```text
Event
 ↓
Impact
 ↓
Secondary Impact
 ↓
Belief Change
 ↓
Intent / Decision
```

# 9. 阶段七：Associative Memory / Trigger 演进

在基础记忆状态稳定后，再引入类似 T-Mem 的 Associative Recall 思想。

这里不直接复制 T-Mem 的业务模型，而吸收其核心思想：

> **在写入时就考虑未来可能通过哪些角度找到这条记忆。**

例如：

```text
Memory:
用户因为上海生活成本太高开始考虑换城市
```

可产生：

```text
Entity Trigger:
上海

Bridge Trigger:
生活成本

Scene Trigger:
考虑换城市

Horizon Trigger:
未来居住规划
```

这些 Trigger 是“触达路径”，不是证据，也不是最终事实。

因此架构变为：

```text
Descriptive Recall
       │
Associative Recall
       │
       ↓
Candidate Memory
       ↓
Memory State Resolver
```

Trigger 负责“找到”，Memory State 负责“判断”。

# 10. 阶段八：Cross-Dimension Coherence

这是 dnamemory 区别于普通向量记忆系统的重要能力。

## 10.1 目标

保证同一个主体、对象和时间范围内：

```text
Event
Fact
Belief
Intent
Impact
```

能够共同解释，而不是相互混淆。

---

## 10.2 合法共存

```text
Fact:
用户目前住上海

Belief:
用户认为上海生活成本高

Intent:
用户考虑离开上海
```

这是正常状态。

---

## 10.3 真正冲突

```text
Fact:
用户在 2026-08 住上海

Fact:
用户在 2026-08 住南京
```

此时进入：

```text
Conflict Resolver
```

依据：

```text
source_rank
confidence
valid_at
observed_at
```

进行状态解析。

# 11. 阶段九：Evidence-First Memory

系统开始从：

```text
“我记得这件事”
```

转变成：

```text
“我记得这件事，并知道为什么记得它。”
```

每个重要 Memory 至少应该能够沿着：

```text
Memory
 ↓
Evidence
 ↓
Original Conversation / Record
 ↓
Timestamp
```

进行追溯。

对于推断记忆：

```text
source = inferred
```

必须明确标识，不能以客观事实形式输出。

# 12. LLM 在项目中的角色演进

## 12.1 0.3.0：LLM 主要承担结构化抽取

```text
文本
 ↓

 ↓

```

同时通过 Pydantic 和确定性兜底降低错误影响。现有设计已经明确采用逐条校验和确定性回退。fileciteturn0file0L30-L35

---

## 12.2 0.4.0：LLM 与 Memory Runtime 解耦

```text
LLM
 ↓
Candidate Memory

Memory Runtime
 ↓
State / Version / Conflict / Temporal / Evidence
```

LLM 不负责最终决定：

```text
当前事实是什么
哪个事实已经失效
哪个观点是当前观点

```

这些由系统规则执行。

---

## 12.3 0.5.x：LLM 参与高级关联，但不是事实引擎

LLM 可以参与：

```text
Trigger Generation
Entity Resolution Hint
Belief Extraction
Impact Candidate Extraction
Natural Language Summary
```

但仍然不能成为：

```text
Fact State Engine
Temporal Engine
Evidence Engine
Conflict Engine
```

---

## 12.4 1.0：LLM 成为 Memory Runtime 的“表达层”

目标：

```text
Memory Runtime
   ↓
Structured Coherent Context
   ↓
LLM
   ↓
Natural Language Response
```

即：

> LLM 负责表达，Memory Runtime 负责记忆状态。

# 22. 项目边界：哪些能力不能被 LLM 接管

为了满足“不是严重依赖大模型”的目标，下列能力必须由系统确定性控制：

```text
事实版本
当前状态
时间排序
有效期
生命周期
删除
权限
证据引用
冲突状态
审计
```

LLM 可以辅助但不能最终决定：

```text
Entity Resolution Hint
Belief Extraction
Impact Extraction
Trigger Generation
摘要
自然语言表达
```

原则：

> **LLM 可以提出 Candidate，但不能直接修改 Ground Truth。**

# 23. 最终业务定位

dnamemory 的产品定位由：

> “给 Agent 增加长期记忆的组件”

逐步演进为：

> **“为 Agent 提供长期状态、历史演化、观点、影响和证据管理的独立 Memory Runtime。”**

最终形成五层能力：

```text
第一层：Remember
记住发生过什么

第二层：Resolve
知道当前是什么状态

第三层：Understand
理解观点、影响和变化

第四层：Associate
能够从不同语义路径找回记忆

第五层：Reflect
形成长期模式与稳定认知
```

最终目标：

```text
Remember
    ↓
Resolve
    ↓
Understand
    ↓
Associate
    ↓
Reflect
```

这五层共同构成 dnamemory 从 MVP 向 Memory Runtime 的完整演进路线。

# 24. 下一阶段实际开发优先级

不建议直接同时开发所有能力。

推荐严格按以下顺序推进：

```text
P0
Memory State Resolver
    ↓
P0
Evidence
    ↓
P0
Temporal Chain
    ↓
P0
Cross-Dimension Coherence
    ↓
P1
Belief / Intent
    ↓
P1
Impact / Valence / Direction
    ↓
P1
Impact Chain
    ↓
P2
Trigger / Associative Recall
    ↓
P2
Memory Consolidation
    ↓
P3
Personal Memory Model
```

原因是：

```text
没有 State Resolver
→ Recall 只是 Top-K

没有 Evidence
→ 无法保证客观性

没有 Temporal Chain
→ 无法保证时间连续性

没有 Coherence
→ 不同维度容易互相污染

没有 Impact
→ 无法表达事情的正负结果

没有 Trigger
→ Associative Recall 只能停留在语义相似层

没有 Consolidation
→ 长期增长后 Memory 会膨胀
```

因此，项目不应首先继续堆 Embedding、Reranker 或更大模型，而应该先把 **Memory State → Temporal Chain → Coherence** 这条核心运行链建立起来，再扩展 Impact 和 Associative Memory。
