# dnamemory 业务改造

> 版本：v0.4.0 设计稿（基于 0.3.0 MVP）  
> 项目：长期个人智能体记忆系统  
> 改造目标：在不严重依赖大模型的前提下，实现事实、事件、观点、意图等不同记忆维度的一致表达，以及可解释的时间链召回、记忆演化与客观连贯性。

---

## 1. 改造背景

当前 0.3.0 MVP 已经具备较完整的记忆基础设施：事件/实体/关系/事实结构化存储，多路召回、RRF 融合、双时态、事实版本链、冲突治理、实体消解、生命周期、受控遗忘、反射压缩以及可选语义模型等能力。现有需求已经明确支持跨会话长期记忆、时间/主题/语义召回和治理能力。

当前主要问题不是“召回能力不够”，而是缺少一层独立于 LLM 的**记忆认知状态层**。现阶段系统能够较好地回答“哪些记忆与问题相关”，但对于以下问题仍需要进一步强化：

1. 同一个对象在不同记忆维度中的表达是否一致；
2. 事实、事件、观点、意图是否能够明确区分；
3. 一个事实发生过多次变化后，系统能否确定“当前有效状态”；
4. 一个观点发生变化后，系统能否保留完整演化历史，而不是简单覆盖；
5. 用户询问“为什么变化”“过去如何变化”“后来发生了什么”时，能否按时间顺序恢复事件链；
6. 每条高价值记忆能否追溯到原始证据；
7. 在没有 LLM、LLM 失败或 LLM 输出不可信时，核心记忆逻辑是否仍然能够运行。

因此，本次业务改造不推翻 0.3.0，而是在现有“多路召回 + 记忆治理”之上增加“记忆状态解析 + 时间链构建 + 证据约束 + 连贯上下文”能力。

---

## 2. 业务目标

### 2.1 总体目标

将 dnamemory 从：

> **长期记忆检索系统**

升级为：

> **具有事实状态、事件历史、观点演化和时间链能力的长期记忆 Runtime。**

核心原则：

```text
LLM 负责理解自然语言
系统负责保存、约束、解析和恢复记忆状态
```

### 2.2 五项核心业务能力

| 能力 | 业务目标 |
|---|---|
| 记忆维度一致性 | Fact / Event / Belief / Intent 等不同维度不混淆 |
| 客观性 | 区分客观发生、用户陈述、系统推断和用户观点 |
| 时间连续性 | 能恢复事件、事实、观点随时间变化的过程 |
| 证据可追溯 | 关键记忆能够追溯到原始对话或结构化来源 |
| 弱 LLM 运行 | 没有 LLM 时，召回、版本解析、冲突和时间链仍然可运行 |

## 3. 核心业务概念改造

### 3.1 从“四类数据”升级为“六类记忆对象”

现有 0.3.0 业务模型为事件、实体、关联边、事实。此次增加 Belief 与 Evidence，并将 Memory State 作为逻辑状态层。

```text
Entity
  │
  ├── Event      发生了什么
  ├── Fact       当前/历史是什么
  ├── Belief     用户/主体怎么看
  ├── Intent     用户准备做什么
  ├── Relation   对象之间如何关联
  └── Evidence   为什么相信这条记忆
```

### 3.2 Event：发生过什么

Event 用于记录已经发生或被明确描述的事件。

典型字段：

```text
subject
predicate
target
occurred_at
source
confidence
evidence_id
```

示例：

```text
2026-08-01
用户去了上海
```

Event 的原则：

- 重点保存发生时间和参与对象；
- 不把主观评价直接写入 Event；
- 事件可与 Fact、Belief、Intent 建立变化关系；
- 同一事件允许存在多个来源证据。

### 3.3 Fact：系统当前认为是什么

Fact 用于表达实体的属性状态，并允许随时间产生版本。

示例：

```text
city = 南京
valid: 2026-03 ~ 2026-07

city = 上海
valid: 2026-07 ~ now
```

业务原则：

- 不覆盖历史事实；
- 当前事实由确定性规则解析；
- 历史事实保留 superseded_by / valid_at / invalid_at；
- 同一个 entity + key 可以存在多个历史版本，但同一查询时刻只能有一个“当前有效状态”或进入冲突态。

### 3.4 Belief：用户/主体怎么看

Belief 是此次改造的重点对象。

它表示：

> 某个主体在某个时间段内对某个命题的看法、评价、判断或主观认知。

示例：

```text
2025-01
上海工作机会多

2026-01
上海生活成本高

2026-08
上海工作机会仍然不错，但不适合长期生活
```

Belief 与 Fact 不做互相覆盖。

允许同时存在：

```text
Fact:
用户目前住上海

Belief:
用户认为上海生活成本高

Intent:
用户考虑离开上海
```

三者不是冲突，而是同一主体在不同认知维度上的状态。

### 3.5 Intent：准备做什么

Intent 用于记录未来倾向、计划或行动意向。

例如：

```text
考虑换工作
准备搬家
以后想减少咖啡摄入
```

Intent 默认不是事实，不应作为“已经发生”的依据。

### 3.6 Evidence：为什么相信

Evidence 是所有高价值记忆的可追溯依据。

来源可以包括：

```text
user_statement
conversation
system_record
external_data
imported_memory
inferred
```

每条 Fact / Event / Belief / Intent 至少尽量绑定一个 evidence。

对于 inferred 类型，必须明确标注“推断”，不能表现成客观事实。

## 4. 记忆可信等级

为避免不同来源混为一谈，新增业务级 Source Rank：

| 来源 | 默认可信级 | 说明 |
|---|---:|---|
| system_record | 5 | 系统确定性记录 |
| external_data | 5 | 外部结构化可信来源 |
| user_statement | 4 | 用户明确陈述 |
| imported_memory | 3 | 外部导入历史记忆 |
| inferred | 1~2 | 系统/模型推断 |

最终置信度建议拆成三个维度，而不是只保留一个数：

```text
source_reliability
extraction_confidence
state_confidence
```

这样系统能够区分：

> “这句话模型抽取得很确定”

和

> “这个事实本身被高可信来源证明”。

两者不是一个概念。

## 5. 业务状态解析

### 5.1 Memory State Resolver

新增统一的 Memory State Resolver，负责将召回到的候选记忆转换为“当前业务状态”。

输入：

```text
Candidate Memories
Query Time
Query Type
Entity Scope
```

输出：

```text
Current Facts
Historical Facts
Events
Beliefs
Intents
Changes
Temporal Chains
Evidence
Conflicts
```

### 5.2 Fact Resolver

对同一：

```text
(entity, key)
```

按以下顺序判断：

```text
1. valid_at / invalid_at
2. source_rank
3. confidence
4. freshness
5. explicit confirmation
```

得到：

```text
current
history
conflict
unknown
```

### 5.3 Belief Resolver

Belief 不进行简单覆盖，而是识别观点变化：

```text
Belief A
  ↓ change
Belief B
  ↓ reinforce
Belief B
  ↓ contradict
Belief C
```

输出观点历史时必须保留：

```text
旧观点
变化时间
新观点
变化证据
当前观点
```

### 5.4 Conflict Resolver

冲突分为：

```text
Hard Conflict
事实在同一有效时刻互斥

Soft Conflict
观点、偏好、态度存在差异

Temporal Conflict
不同时间都成立

Source Conflict
不同来源给出不同结果
```

不同类型采用不同治理策略，不能统一覆盖。

## 6. 时间链业务模型

### 6.1 从时间排序升级为时间链

现有 time recall 解决“时间接近”，此次改造成解决“时间演化关系”。

```text
Event A
  │ before
  ↓
Event B
  │ caused_change
  ↓
Fact C
  │ triggered
  ↓
Belief D
```

### 6.2 时间链类型

建议增加以下逻辑关系：

| 关系 | 含义 |
|---|---|
| before | A 发生在 B 之前 |
| after | A 发生在 B 之后 |
| overlaps | 时间范围重叠 |
| changes | A 导致 B 状态变化 |
| reinforces | A 强化 B |
| contradicts | A 与 B 存在观点/事实冲突 |
| supersedes | B 替代 A |
| caused_by | B 的状态变化可追溯至 A |
| summarizes | 摘要概括 A |

这些关系不要求全部由 LLM 生成，能够由时间字段、事实版本、显式来源和已有边进行确定性推导。

### 6.3 时间链召回模式

新增查询意图：

```text
current_state
history
change
why_change
timeline
comparison
```

例如：

```text
“我现在住哪里？”
→ current_state

“我以前住哪里？”
→ history

“我什么时候搬到上海的？”
→ timeline

“我为什么开始考虑离开上海？”
→ why_change

“我对上海的看法发生过什么变化？”
→ change
```

Query Type 不要求 LLM 判断，可以优先通过规则/关键词/过滤条件确定；LLM 仅作为可选增强。

## 7. 召回业务改造

### 7.1 原流程

```text
Query
 ↓
Time / Graph / Dense / Sparse
 ↓
RRF
 ↓
Reranker
 ↓
Top-K
```

### 7.2 新流程

```text
Query
 ↓
Query Type
 ↓
Candidate Retrieval
 ├─ Time
 ├─ Graph
 ├─ Dense
 └─ Sparse
 ↓
RRF
 ↓
Memory State Resolver
 ↓
Temporal Chain Builder
 ↓
Evidence Validator
 ↓
Memory Coherence Check
 ↓
Context Builder
 ↓
LLM（可选）
```

### 7.3 重要原则

RRF 只负责：

> 找到相关候选。

RRF 不负责：

> 决定当前事实、观点是否有效、历史应该如何解释。

最终答案上下文必须经过 Memory State Resolver。

## 8. 典型业务案例

### 案例 A：当前状态

记忆：

```text
2025-01 北京
2025-08 南京
2026-07 上海
```

查询：

```text
“我现在住哪里？”
```

期望：

```text
上海
```

而不是三个地点按向量相似度排序后直接交给 LLM。

### 案例 B：历史回放

查询：

```text
“我过去几年住过哪些地方？”
```

期望：

```text
2025-01 北京
→ 2025-08 南京
→ 2026-07 上海
```

要求保持时间顺序。

### 案例 C：观点变化

查询：

```text
“我以前怎么看上海，现在怎么看？”
```

期望结构：

```text
过去：认为上海工作机会多
↓
后来：认为生活成本较高
↓
现在：认为工作机会仍然不错，但不适合长期生活
```

### 案例 D：事实与观点共存

```text
Fact:
目前住上海

Belief:
上海生活成本高

Intent:
考虑离开上海
```

系统必须判断三者是一致的多维认知，而不是冲突事实。

### 案例 E：证据不足

查询：

```text
“我为什么离开南京？”
```

如果只有：

```text
2026-07 搬到上海
```

但没有明确原因，则输出：

```text
已确认：2026-07 从南京搬到上海。
未发现足够证据证明搬迁原因。
```

不得自行编造原因。

## 9. LLM 使用边界

### 9.1 必须依赖 LLM 的环节

```text
自然语言 → 候选结构化记忆
复杂语言中的主体/关系识别
最终自然语言表达
```

### 9.2 不应严重依赖 LLM 的环节

```text
事实版本判断
时间排序
事实当前状态
superseded_by
证据绑定
生命周期
冲突治理
时间链拼接
召回过滤
权限
删除
审计
```

### 9.3 LLM 失败降级

当 LLM：

- 超时；
- 返回非法 JSON；
- Pydantic 校验失败；
- 置信度异常；
- 服务不可用；

系统仍允许：

```text
结构化 API 写入
时间召回
图谱召回
事实版本链
冲突治理
时间链
```

## 10. 评测指标改造

现有评测覆盖 temporal / multi_hop / update / abstain / paraphrase，并已经有 Recall@5、MAP@5 等门禁。此次新增“状态正确性”评测。

| 指标 | 目标 |
|---|---|
| Recall@5 | 保留现有门禁 |
| MAP@5 | 保留现有门禁 |
| Current Fact Accuracy | 当前有效事实识别正确率 |
| Temporal Ordering Accuracy | 时间链顺序正确率 |
| Belief Evolution Accuracy | 观点变化链正确率 |
| Evidence Grounding Rate | 有证据支撑的记忆占比 |
| Conflict Resolution Accuracy | 冲突解析正确率 |
| Abstain Accuracy | 证据不足时正确拒答率 |
| Cross-Dimension Coherence | 多维记忆一致率 |

### 10.1 最关键的新增指标

#### Temporal Ordering Accuracy

对于：

```text
A < B < C
```

召回后的排序必须保持：

```text
A → B → C
```

#### Current Fact Accuracy

问：

```text
“现在在哪里？”
```

只能返回当前有效版本。

#### Belief Evolution Accuracy

要求同时判断：

```text
旧观点
变化节点
新观点
```

不能只看最终观点。

#### Cross-Dimension Coherence

验证：

```text
Fact
Event
Belief
Intent
```

之间能否同时成立，并正确解释冲突与时间差异。

## 11. 版本路线

### 0.4.0：记忆认知层

优先完成：

1. Belief / Intent 数据模型；
2. Evidence 模型；
3. Memory State Resolver；
4. Temporal Chain Builder；
5. Context Builder；
6. 当前事实确定性解析；
7. 时间链测试集。

### 0.4.1：一致性治理

增加：

1. Cross-Dimension Coherence；
2. Belief Conflict；
3. Evidence Grounding；
4. Change Reason / Cause 链；
5. 复杂时间范围处理。

### 0.5.0：长期认知压缩

在已有 Reflection 的基础上进一步实现：

```text
Raw Memory
 ↓
Episode
 ↓
Theme
 ↓
Temporal Summary
 ↓
Stable Memory
```

摘要只能压缩表达，不能替代原始证据。

## 12. 本次业务改造边界

本次改造不做：

- 推翻 SQLite 存储；
- 推翻现有 RRF；
- 强制引入 Neo4j / PostgreSQL；
- 强制依赖更大的 LLM；
- 用 LLM 重新解释所有历史数据；
- 以向量相似度代替事实状态。

本次改造重点：

> **让已有的记忆数据“具有状态、具有时间、具有证据、具有维度、能够形成演化链”。**

## 13. 改造后的最终业务闭环

```text
用户对话
   ↓
候选记忆抽取
   ↓
Pydantic 校验
   ↓
Event / Fact / Belief / Intent
   ↓
Evidence 绑定
   ↓
Entity Resolution
   ↓
Version / Conflict Governance
   ↓
Memory State
   ↓
Temporal Chain
   ↓
Memory Retrieval
   ↓
Coherent Context
   ↓
LLM Response
```

最终希望形成的业务能力不是：

> “我能从数据库找到几条相关记忆。”

而是：

> “我能确定哪些事情发生过、哪些事实现在有效、用户过去和现在分别怎么看、这些变化在什么时候发生、有什么证据，以及这些记忆之间是否能够同时成立。”
